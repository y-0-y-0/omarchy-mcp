## Source evidence and results

Two independent subagents reviewed the exact upstream releases. Main finding: the project is not fully compatible as a desktop automation server because dispatch-dependent actions are unconditionally disabled in `hyprland_mcp/hyprctl.py:33-41`; launching applications is separately disabled in `server.py:274-281`. Do not infer that the other tools work from these observations.

Hyprland 0.57.0 ([release](https://github.com/hyprwm/Hyprland/releases/tag/v0.57.0), tag commit [0aa6745](https://github.com/hyprwm/Hyprland/tree/0aa6745f705f2c4b0a5004eb019ef76e5bbdb426)) removed legacy configuration support. The [versioned hyprctl documentation](https://wiki.hypr.land/0.57.0/configuring/core/advanced-configuration/using-hyprctl/) says dispatch evaluates a Lua dispatcher expression; the [tagged implementation](https://github.com/hyprwm/Hyprland/blob/0aa6745f705f2c4b0a5004eb019ef76e5bbdb426/src/ipc/s1/Commands.cpp#L1332-L1349) wraps the input in `hl.dispatch(...)`. Re-enabling the existing legacy argument construction without a safe Lua interface would be incorrect and potentially unsafe.

Static JSON contract comparison: the tagged implementation emits the monitor fields consumed by the project ([monitor formatter](https://github.com/hyprwm/Hyprland/blob/0aa6745f705f2c4b0a5004eb019ef76e5bbdb426/src/ipc/s1/Commands.cpp#L220-L290)); window fields including numeric monitor ID ([window formatter](https://github.com/hyprwm/Hyprland/blob/0aa6745f705f2c4b0a5004eb019ef76e5bbdb426/src/ipc/s1/Commands.cpp#L441-L516)); workspace `name`, `monitor`, `windows` and an optional numerical `id` ([formatter](https://github.com/hyprwm/Hyprland/blob/0aa6745f705f2c4b0a5004eb019ef76e5bbdb426/src/ipc/s1/Commands.cpp#L612-L630)); an empty object when no active window exists ([handler](https://github.com/hyprwm/Hyprland/blob/0aa6745f705f2c4b0a5004eb019ef76e5bbdb426/src/ipc/s1/Commands.cpp#L751-L762)); and global cursor coordinates ([handler](https://github.com/hyprwm/Hyprland/blob/0aa6745f705f2c4b0a5004eb019ef76e5bbdb426/src/ipc/s1/Commands.cpp#L1383-L1395)). `list_workspaces` handles absent IDs, but `list_windows` only supports numeric workspace filters, excluding named workspaces without IDs.

The monitor geometry source uses physical pixel size, transform and scale ([Hyprland Monitor.cpp](https://github.com/hyprwm/Hyprland/blob/0aa6745f705f2c4b0a5004eb019ef76e5bbdb426/src/output/Monitor.cpp#L997-L1004)); the project follows similar math but deliberately rejects non-integral logical dimensions, overlaps and desktop bounding boxes containing gaps. It checks all monitors even for a targeted capture. Hyprland emits window geometry from its target geometry, which may not equal rendered position during animations ([window formatter](https://github.com/hyprwm/Hyprland/blob/0aa6745f705f2c4b0a5004eb019ef76e5bbdb426/src/ipc/s1/Commands.cpp#L495-L500)). Therefore a source match is not proof that grim captures or mapped coordinates work on real displays.

Omarchy [v4.0.6](https://github.com/omacom/omarchy/releases/tag/v4.0.6), tag commit [237f1b4](https://github.com/omacom/omarchy/tree/237f1b4071a0bff2296c6d740ba2b9fd695ebfa0), loads its [Lua bootstrap and user configuration](https://github.com/omacom/omarchy/blob/237f1b4071a0bff2296c6d740ba2b9fd695ebfa0/config/hypr/hyprland.lua). The [base package manifest](https://github.com/omacom/omarchy/blob/237f1b4071a0bff2296c6d740ba2b9fd695ebfa0/install/omarchy-base.packages) lists hyprland, grim, wtype, wl-clipboard, tesseract and English Tesseract data. It does not specify a Hyprland version; an Omarchy version does not establish the installed Hyprland version. `ydotool` was not found in the inspected base and other package manifests, but this does not establish whether it exists on a particular machine; its daemon and uinput permissions are also required. UWSM configures the session, but inheritance by the particular MCP client remains unverified. Do not run `omarchy-refresh-hyprland`: it can replace user configuration.
